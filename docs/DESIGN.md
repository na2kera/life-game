# life-game 設計書

人生ゲーム風の 3D ボードゲーム。PC ブラウザで 2〜4 人が 1 台の端末を交代して遊ぶ。

## 0. 方針

- 参考にするのは現代のスタンダード版人生ゲームの「仕組み」（ルーレット、職業、結婚、家、ゴール時の資産計算）。
- **公開予定のため、名称・ロゴ・盤面デザイン・カード文面は原作をそのまま使わない。** ゲーム内の固有名（タイトル、職業名、マスの文言）はオリジナルにする。仕組み自体は著作権の対象外。
- まず短縮版（約 30 マス）で一周遊べる状態を作り、その後マスを原作相当まで増やす。
- 3D モデルは Blender で自作して glb で読み込む。モデル完成前はコードで作った仮形状で動かす。

## 2. アーキテクチャ

三層に分け、依存は一方向（view/ui/input → core）にする。core は three.js や DOM に一切依存しない。

```
src/
  core/        ゲームルール。純粋 TS。Vitest でテスト
    types.ts       Player, Space, GameState, GameEvent などの型
    board.ts       マスの定義と経路（データ駆動）
    rules.ts       ルーレット結果の適用、マス効果、ゴール判定、資産計算
    game.ts        状態機械（ターン進行）。入力は「アクション」、出力は「イベント列」
    rng.ts         シード付き乱数（テスト再現用）
  data/        盤面・職業・イベントのデータ（JSON 相当の TS）
    board-short.ts 短縮版 30 マス
    jobs.ts        職業一覧（名称はオリジナル）
  view/        three.js による描画
    scene.ts       レンダラー、ライト、カメラ
    board-view.ts  マスの配置（core の座標データから生成）
    piece-view.ts  コマ。移動アニメーション
    roulette-view.ts ルーレット演出
    assets.ts      glb ローダー。未配置なら仮形状にフォールバック
    camera.ts      コマ追従カメラ
  ui/          HTML オーバーレイ
    hud.ts         所持金・職業・ターン表示
    dialog.ts      選択肢ダイアログ（職業選択、家購入など）
    log.ts         イベントログ
  input/
    input.ts       「決定・キャンセル・上下左右」の抽象入力
    gamepad.ts     Gamepad API 実装
    keyboard.ts    キーボード実装
  app.ts       core・view・ui・input をつなぐ進行役
  main.ts      エントリ
```

### core の設計

- `GameState` はイミュータブルに扱う。`applyAction(state, action) -> { state, events }`。
- `action`: `spin`, `choose(optionId)`, `next`。
- `events`: `moved(from, to, path)`, `moneyChanged`, `jobAssigned`, `married`, `childBorn`, `houseBought`, `goal`, `turnChanged` など。view と ui はイベント列を順に演出する。
- 乱数はシード付きで state に含め、同じシードなら同じ展開になる（テストと再現性のため）。

### view の設計

- 盤面の座標は `board.ts` の各マスが持つ `position: {x, z}` から生成する。Blender で盤面全体を作らず、マスのモデルを並べる。
- コマの移動は 1 マスずつ跳ねるアニメーション。events の `moved.path` を順に消費する。
- ルーレットは結果を先に決めてから、その結果に止まるように回す演出。
- 単位はメートル。マス 1 個 = 1m 四方。モデルの原点は底面中央。

### input の設計

- 抽象入力は `confirm`, `cancel`, `up`, `down`, `left`, `right` の 6 つ。
- **Joy-Con を主対象にする。** Joy-Con は Bluetooth で片側ずつ別のゲームパッドとして認識され、Chrome では `mapping` が `standard` にならない。`gamepad.id` に `Joy-Con (L)` / `Joy-Con (R)` を含むかで判定し、横持ち（SL/SR を上にした持ち方）前提の専用マッピングを持つ。
  - 横持ちで「決定」= 右側の下ボタン（R なら A、L なら 下方向ボタン）、「キャンセル」= その隣、「上下左右」= スティック。実機で検証して `input/joycon.ts` に定数として置く。
  - L と R で方向軸の向きが 90 度ずれるので、片側ごとに回転補正する。
- Pro コントローラーは `standard` マッピングで認識されるので標準の割り当てを使う。
- 未知のコントローラー向けに「ボタン設定画面」（決定・キャンセルを実際に押して割り当てる）を用意し、Joy-Con の判定が外れた場合の逃げ道にする。
- コントローラー未接続時はキーボード（Enter / Esc / 矢印）で同じ操作ができる。
- 交代プレイなので Joy-Con 1 本を全員で回す前提。両方接続されていればどちらでも操作できるようにする（複数人同時操作は不要）。

## 3. ゲームルール（短縮版 v1）

現代のスタンダード版の仕組みを参考にする。マス数は短縮するが、要素（カード・保険・株・借金）は v1 から入れる。金額や枚数はすべて `data/` の定数で調整できるようにする。

### 基本
- プレイヤー 2〜4 人。初期所持金 ¥30,000。
- ルーレットは 1〜10。
- スタート直後に分岐: 「進学ルート」（遠回り、職業を選べる）と「就職ルート」（近道、職業はランダム）。
- 職業は給料額を持つ。「給料マス」を通過または停止で給料を受け取る。
- 「結婚マス」は必ず止まる。以降「子供マス」で子供が増える。
- 「家マス」で家を買える（選択）。家は価格と最終評価額を持つ。
- 「転職マス」で職業を引き直せる。
- 「イベントマス」はお金の増減。損失には種別（病気・火事・事故・その他）がある。

### カード
- **イベントカード**: 「カードマス」に止まると山札から 1 枚引き、即時に効果を適用する（お金の増減、指定マスへ移動、他プレイヤーから徴収など）。
- **所持カード**: 一部のカードは手札に入り、任意のタイミングで使える（例: ルーレットの出目を +1 する、損失イベントを 1 回無効化する、他人の給料を奪う）。手札上限は 3 枚。
- ゴール時に残った所持カードは 1 枚あたり一定額で換金する。
- カードの効果は `data/cards.ts` に効果種別 + パラメータで定義し、ルール側は効果種別ごとの処理だけを持つ。

### 保険
- 「保険マス」で生命保険・火災保険・自動車保険を購入できる（各 1 口、価格固定）。
- イベントやカードの損失種別に対応する保険を持っていれば、その損失を免除する。
- 保険はゴール時の資産には含めない（掛け捨て）。

### 株
- 「株マス」で株券を 1 枚購入できる（1 枚 ¥5,000、所持上限 3 枚）。
- 「株価変動マス」に誰かが止まると、ルーレットの出目で全員の株価が上下する（変動表は data に置く）。
- ゴール時に現在の株価 × 枚数で換金する。

### 借金
- 支払い時に所持金が足りなければ、自動で ¥10,000 単位の借用証書を発行して補填する。
- 借用証書 1 枚はゴール時に ¥12,000 で返済する（利子 ¥2,000）。途中でも給料受け取り時に任意で返せる。

### ゴール
- 総資産 = 所持金 + 家の評価額 + 株の換金額 + 所持カード換金額 + 子供 1 人あたりボーナス − 借用証書の返済額。
- 総資産が最も多い人が勝ち。全員がゴールした時点で結果画面を出す。

## 4. 画面構成

- 中央: 3D 盤面。カメラは現在手番のコマを斜め上から追従。
- 右上: 全プレイヤーの所持金・職業・家族（HUD）。
- 下部: 現在の案内（「A ボタンでルーレットを回す」など）と選択肢ダイアログ。
- 左下: 直近のイベントログ。
- 色・レイアウトの細部は実装時に提案し、合意してから決める。

## 5. マイルストーン

1. **M1 core**: 型・盤面データ・ルール・状態機械をテスト付きで実装。UI なしで一周通る。
2. **M2 view 最小**: 仮形状の盤面とコマ、ルーレット演出、追従カメラ。キーボードで遊べる。
3. **M3 ui + gamepad**: HUD・ダイアログ・ログ。Switch コントローラー対応。
4. **M4 assets**: Blender モデルの読み込みと差し替え。
5. **M5 拡張**: マス数を原作相当に、カード・保険などの追加要素。

## 6. 開発ルール

- 実装は Opus、設計は Fable、レビューは Fable と Codex。
- core の変更にはテストを付ける。`npm run check`（lint・typecheck・test・build）が通ってから PR。
- マス・職業・イベントはすべてデータファイルに置き、ルール本体にハードコードしない。
